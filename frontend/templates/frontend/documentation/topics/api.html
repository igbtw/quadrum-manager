Quadrum exposes JSON endpoints used by the point of sale and the global search. They live in frontend/views.py and are registered in frontend/urls.py. All of them require an authenticated session.

Endpoint overview

Method and pathPurpose
POST /api/pos/calculate/Calculate a cart total from stored product data (read-only).
POST /api/pos/finalize/Finalize a sale atomically, with idempotency.
GET /api/search/?q=termGlobal search used by the command palette.
POST /api/pdv/calcular/, POST /api/pdv/finalizar/Legacy aliases of the two POS endpoints, kept for compatibility.

Authentication, methods, and CSRF

  • Every endpoint is protected by sign-in; an anonymous request is redirected to /login/ (302), not answered with a 401/403.
  • The POS endpoints are POST-only; an authenticated non-POST request returns 405. The search endpoint is GET-only.
  • State-changing requests must carry a CSRF token, sent as the X-CSRFToken header or the csrfmiddlewaretoken form field.
  • The POS endpoints read a JSON body (application/json) directly.

Calculate total

  • Request: {"items": [{"product_id": 12, "quantity": 2}]}.
  • product_id and quantity must be positive JSON integers — booleans, floats (including 2.0), strings, null, zero, and negatives are rejected with 400. A missing quantity is rejected.
  • A valid id that matches no active product returns 404; client-supplied prices are ignored.
  • Success: {"total": "10.00"} — the total is a string with two decimals. An empty items list returns {"total": "0"}.
  • The endpoint is read-only: it does not reserve or guarantee stock.

Finalize sale

  • Request fields: items (non-empty), optional customer_id (must be an active person), optional payment_method (exactly one of CASH, DEBIT, CREDIT, PIX, ON_ACCOUNT), and a required idempotency_key (1–255 characters, letters, digits, _ and -).
  • Success returns {"success": true, "code": "VEN-000042", "message": "Sale completed"}.
  • Side effects on a new sale (all in one atomic transaction): one Sale, one SaleItem per line with the stored unit price, stock reductions with a stock movement per item, and — for On Account sales with a customer — one account receivable.
  • Insufficient stock is a business conflict (409 {"error": "Insufficient stock"}), not a server error; every write rolls back, so stock never goes negative.

Idempotency and retries

  • The request fingerprint is a SHA-256 over the normalized items (sorted product_id/quantity pairs), customer_id, and payment_method; item order and any client price are excluded.
  • Retrying with the same key and equivalent contents returns the original sale code with 200 and writes nothing new.
  • Reusing a key with different contents returns 409; a key owned by another user returns 403.

Search endpoint

  • GET /api/search/?q=term searches pages, documentation topics, products, people, and sales, returning up to five results per group.
  • The query is whitespace-normalized and capped at 100 characters; at least two characters are required.
  • The advanced prefixes page:, doc:, product:, person:, and sale: restrict the search to one group; an empty prefixed term returns a prompt instead of results.
  • People results are matched on name and record/doc and never include email or phone fields.

Error summary (finalize)

StatusWhen
400Empty cart, malformed items, invalid payment method, or invalid idempotency key.
403Idempotency key belongs to another user.
404customer_id provided but no active person matches.
409Key conflict (different contents), incomplete prior attempt, or insufficient stock.
500Unexpected failure; the response carries no internal detail.

The complete request/response schemas, every controlled error message, and the fingerprint rules are documented in docs/api-reference.md and docs/business-flows.md (repository files, not served by the application). See also Search and Advanced Queries.
